# 小黎 AI 开发流程（通用版）

AI 与用户按 TAPD 条目开发时共同遵守。本文只定通用骨架与规则；项目专属的信息不写在这里，按第 0 节去读或去问。

## 0 开工前：定下项目信息

1. 读项目内 `docs/xiaoli/workflow.md` 与 `docs/xiaoli/resources.md`，再读 `AGENTS.md`、`CLAUDE.md` 等项目规则。项目内文档与本文冲突时听项目的。
2. 开工消息里带了「项目资料目录」时（工作台全局模式，`~/.claude/xiaoxiaoli/projects/<项目键>/`），读其中的 `resources.md`；测试账号等密钥在其中的 `secrets.env`，只读取使用，不回显，不写进仓库、评论或文档。开工消息里还带了「通用资料目录」时（`~/.claude/xiaoxiaoli/shared/`，各项目共用），先读它里面的同名文件，再读项目的；两处都写了同一项时听项目的。
3. 开工消息要求先取工作流时，调 `mcp__xiaoxiaoli__workflow` 取，以它返回的步骤、细则与「先问」要求为准；第 2、3、4 节的环节表是前端的默认版本，其他工种或自定义过的项目与它不同。
4. 下面几项缺哪项问用户一次，答案记下来，之后不再问。记在哪：所有项目都一样的记进通用资料目录，只属于本项目的记进项目资料目录，拿不准问用户一次；两处目录都没有时问用户记在哪。不往项目仓库里新建配置文件。
   - TAPD 项目 ID（workspace_id）与用户在 TAPD 的昵称
   - 分支起点（默认 `origin/master`）与分支命名规则
   - 单测、门禁、本地启动的命令，已知的假失败
   - 测试环境地址、测试账号放在哪、允许写入的测试数据范围
   - 发版方式（谁触发、哪些环境、怎么验收）、文档放哪、语雀知识库
5. 测试账号可以有多组，同一个项目里不同功能用不同的账号和数据是常态：
   - `secrets.env` 里每组账号前面用一行注释写清组名与用途，如 `# [运营-审核员] 用于审核流程、权限相关功能`；同组的变量用同一个前缀。组对应的地址、测试数据范围等不是密钥的说明，记在同目录 `resources.md` 里同名的小节下。
   - 用户给了新账号就追加成新的一组，不覆盖、不删除已有的组；只有用户明确说某一组换了，才改那一组，改之前说清要改的是哪组。
   - 自测前按要测的功能挑用途对得上的那一组；对不上，或有几组都合适，问用户用哪组，不自己猜。用了哪一组（只写组名）写进自测结论。

## 1 进度上报

- 有 `mcp__xiaoxiaoli__progress` 工具时，每推进一步、换当前子项、派子代理时调一次：`id` 填 TAPD 短 ID，`step` 用下表的键，`status` 填 `doing` 或 `done`，`detail` 写当前子项；等用户拍板时传 `waiting`（`align` 对齐稿、`review` 看自测、`tapd` 批准改 TAPD，`none` 清掉）；结论要用户确认的步传 `confirm: true`。不手改它的状态文件。
- 没有这个工具（Codex 等其他 AI）就跳过，在对话里用一两行说明进行到哪步。

## 3 环节细则

### ① 拉取 TAPD

- 用户待办：`get_todo`，`entity_type` 分别取 `story`、`task`、`bug`；按字段筛用 `get_stories_or_tasks`（`entity_type` 为 `stories` 或 `tasks`）、`get_bug`。
- 清单列 ID、标题、状态、优先级、预计开始、预计结束；拉取不改任何状态。
- 装了小小黎面板时由面板拉取与展示，用户在面板点「开工」（发出 `开工 <ID>`）后才处理。

### ② 排序

- 排序键依次为优先级、预计开始、预计结束；优先级候选值用 `get_stories_fields_info` 查，未配置时为 High、Middle、Low、Nice To Have。
- 由用户选定一条，收到 `开工 <ID>` 再往下走。

### ③ 建分支

- `git worktree add --no-track -b <分支> <目录> <起点>`，或 `git switch --no-track -c <分支> <起点>`；起点与命名按第 0 节。小小黎面板生成的启动命令已按此写好。
- 远程首次建分支：用户同意后 `git push -u origin <分支>:<分支>`。交付前跑 `git status -sb`，不在主干却显示上游是 `origin/master` 当异常告诉用户。

### ④ 读需求与语雀

- 正文：`get_stories_or_tasks` 传 `id`，`fields` 带 `description`；附件 `get_entity_attachments`（下载链接有效期短，拿到就读）；正文图片 `get_image`；评论 `get_comments`。
- 需求里的语雀链接用 li-yuque-skills 读，原型 HTML 常在语雀文档内。

### ⑤ 对齐需求

- 拿到需求先对齐一次：输出需求摘要、疑问、方案、影响文件范围四段，`waiting` 记 `align`，用户确认前不改代码。
- 过程中出现歧义随时再对齐，不猜。接口契约查项目的接口文档（如 Apifox，项目号见 `resources.md`）。

### ⑥ 开发

- 项目规则（`AGENTS.md`、工程文档、lint 与格式化配置）优先，没定死的按项目内 `code-style.md`（有的话）。
- 小步提交，一次一个可说明的改动；本地提交要不要逐次确认按项目约定，没约定先问一次；推送一律先问。
- 设计稿用 figma MCP，三方库文档用 context7 MCP。少碰无关文件，不顺手重排格式。

### ⑦ 单测

- 测试与被测模块就近放；跑项目的单测与门禁命令（见 `resources.md` 或 `package.json` 的 scripts）。
- 只报真实失败；已知的本机假失败记进 `resources.md`，不当判据。

### ⑧ 浏览器自测

- 用 chrome-devtools MCP 另起的受控浏览器，它不共享日常浏览器的登录态，要在受控窗口里登录测试账号。
- 账号从 `secrets.env` 读，只读不回显；后端写入会落库，写操作先问，且只在约定的测试数据范围内做。
- 修缺陷先在受控浏览器里按原步骤复现；日志与复盘写到项目约定的被忽略目录，不在仓库根乱建目录。
- 自测完 `waiting` 记 `review`，附结论与截图给用户看。

### ⑨ 写文档

- 写之前先和用户定：哪些值得记、写给谁看、提纲是什么；文档内容由用户定稿，不自己拍板。
- 项目文档按项目规范放进仓库；新增文档要登记的索引、速查表属于团队共享文件，改前先问。
- 分享类文档写完先给用户预览，确认后用 li-yuque-skills 上传。

### ⑩ 更新 TAPD

- 写前按 ID 重查：处理人有用户、状态与预期一致才写；流转前用 `get_workflows_all_transitions` 查可去的状态与必填字段，流转时显式传处理人和必填字段，不依赖默认值。
- 写工具：`update_story_or_task`（`v_status` 改状态）、`update_bug`、`create_comments`。本人任务按项目约定流转并发【完成】；他人条目一律先问。
- 评论格式见第 5 节；同一标签、同一提交已发过就不重发；发前扫一遍有没有凭据、本地路径。

### ⑪ 发版

- 发版前检查：本地与远程一致；门禁与构建通过；列出自上次部署以来的提交、共享文件、依赖变化与风险，给「可发 / 不建议发」结论。
- 触发：按 `resources.md` 的方式；能 dry-run 的先把将触发的内容给用户看一眼；生产环境只出检查结论，由用户自己点。
- 发版后验收：核版本号、本次涉及的路由与主流程、控制台报错；有问题给回滚建议，由用户定。发版后在需求上发【发版】评论。

## 4 缺陷 6 步

缺陷只在用户点「开工」或说「开工 <缺陷 ID>」后才处理；状态名与流转按项目的 TAPD 工作流查，不猜。

| 步 | 键 | 做什么 |
| --- | --- | --- |
| 1 读截图 | `screenshot` | 预检（处理人有用户、状态是未解决或重新打开）；读描述与全部截图（`get_image`） |
| 2 核环境版本 | `env` | 核被报环境的版本号与提交，确认问题版本 |
| 3 复现 | `reproduce` | 本地、测试环境同账号、同数据各试一轮；一轮复现不了就在条目上发【请补信息】（先问） |
| 4 定位判定 | `diagnose` | 定位根因，出判定稿：前端问题写根因与改法；非前端问题写目标状态、处理人与评论草稿；`waiting` 记 `align` |
| 5 修复或拒绝 | `fix` | 用户同意后才动：前端问题改代码、补单测、本地提交（正文末尾 `TAPD: <缺陷短 ID>`）；拒绝、转产品、转后端按判定稿落状态并发评论；结论要用户确认时传 `confirm` |
| 6 验证 | `verify` | 发到测试环境后按原步骤验证，通过后按项目流程改状态并发【已修复】 |

## 5 通用规则

### 对齐确认前不改代码

需求先过⑤，缺陷先过第 4 步的判定稿；用户明确确认后才动代码或 TAPD 状态。

### 必须先问的动作

- TAPD：他人条目上的评论、状态或处理人；缺陷改代码前的根因与改法；缺陷的拒绝、转产品、转后端、无法复现；新建需求、任务、缺陷
- `git push`
- 语雀上传
- 后端的写操作
- 安装全局工具
- 修改团队共享文件（`.gitignore`、`package.json`、文档索引等配置文件）
- 删除目录

### Git 铁律

- 绝不推主干（`master`、`main` 等）；合主干只走 MR，由用户操作。
- 推送一律显式写目标：`git push origin <本地分支>:<同名远程分支>`，不依赖上游。
- 以远程分支为起点建分支必须 `--no-track`，或建完立刻 `git branch --set-upstream-to=origin/<同名分支>`。

### 提交

- 标题 `type(scope): 中文具体变化`，type 取 `build`、`chore`、`ci`、`docs`、`feat`、`fix`、`perf`、`refactor`、`revert`、`style`、`test`；正文写原因、影响、验证，末尾一行 `TAPD: <短 ID>`。
- 不带 AI 署名与 `Co-Authored-By` 页脚；只暂存本次相关路径，不提交 `.env*.local` 与凭据。项目有 commitlint 等约定时以项目为准。

### TAPD 评论格式

- 评论是富文本 HTML，不是 Markdown：一行一个 `<p>`，开头放【标签】（如【完成】【发版】【请补信息】），全条不超过 10 行。
- @ 人用 `<b class="at-who" contenteditable="false" data-userid="昵称" data-type="user">@昵称</b>`，纯文本 @ 不会通知到人。
- 要别人办的事用可勾选清单 `<ul class="tox-checklist"><li>事项 @负责人</li></ul>`，每项末尾 @ 该项负责人；已经办完的项写成 `<li class="tox-checklist--checked">`。
- 署名：开工消息里带了「TAPD 评论署名 ——某某AI工作台」时，评论末尾空一行 `<p><br /></p>`，再加 `<p style="text-align: right;">——某某AI工作台</p>`，名称照抄开工消息里的；开工消息没带、项目规则也没要求时不署名。
- 只引用提交短号、路由、版本号、语雀链接，不写本地路径与内部草稿编号。发错了用 `update_comments` 原地改，不删了重发。
